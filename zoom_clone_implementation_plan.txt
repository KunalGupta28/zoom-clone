
ZOOM CLONE — SENIOR DEVELOPER IMPLEMENTATION PLAN
=================================================

Purpose
-------
This document converts the Zoom Clone assignment analysis into an execution-ready
implementation blueprint for a one-day development window.

The goal is NOT to build a production-scale replacement for Zoom. The goal is to
deliver a polished, functional Zoom-like video conferencing platform that:

1. Satisfies every mandatory requirement.
2. Implements the highest-value bonus features.
3. Has a strong relational database design.
4. Uses clean, modular frontend/backend architecture.
5. Resembles the modern Zoom UX closely.
6. Can be deployed and demonstrated reliably.
7. Can be explained confidently during the evaluation interview.

WHY LIVEKIT?
------------

A hand-built WebRTC/P2P system requires signaling, SDP negotiation, ICE
candidate handling, peer discovery, reconnect behavior, track management,
and network edge-case handling.

For a one-day assignment, that creates unnecessary implementation risk.

LiveKit provides a production-oriented WebRTC/SFU layer while allowing the
application's UI, meeting lifecycle, database, APIs, and host controls to
remain custom.

Preferred priority:
LiveKit > MediaSoup > hand-built P2P

provided the implementation team can explain LiveKit's role clearly.

6. DATABASE DESIGN — RECOMMENDED
=====================================

The assignment explicitly evaluates database design.

The schema should demonstrate:
- Normalized relationships.
- Foreign keys.
- Unique meeting codes.
- Participant-to-meeting relationships.
- Meeting lifecycle.
- Timestamps.
- Guest participation without requiring authentication.

  TEXT UNIQUE NOT NULL

  TEXT NULL

created_at
  DATETIME NOT NULL


TABLE: meetings
---------------

id
  INTEGER PRIMARY KEY AUTOINCREMENT

meeting_code
  TEXT UNIQUE NOT NULL

title
  TEXT NOT NULL

description
  TEXT NULL

  INTEGER NOT NULL
  FOREIGN KEY -> users.id

scheduled_at
  DATETIME NULL

  INTEGER NOT NULL

status
  TEXT NOT NULL

invite_slug
  TEXT UNIQUE NOT NULL

created_at
  DATETIME NOT NULL

started_at
  DATETIME NULL

ended_at
  DATETIME NULL


MEETING STATUS VALUES
---------------------

scheduled
active
ended
cancelled


TABLE: meeting_participants
---------------------------

id
  INTEGER PRIMARY KEY AUTOINCREMENT

meeting_id
  INTEGER NOT NULL
  FOREIGN KEY -> meetings.id

user_id
  INTEGER NULL
  FOREIGN KEY -> users.id

display_name
  TEXT NOT NULL

role
  TEXT NOT NULL

joined_at
  DATETIME NOT NULL

left_at
  DATETIME NULL


WHY user_id CAN BE NULL
-----------------------

Authentication is not required.

Example registered/default user:
- user_id = 1
- display_name = "Kunal"

Example guest:
- user_id = NULL
- display_name = "Rahul"


RELATIONSHIPS
-------------

users 1 ---- N meetings
users 1 ---- N meeting_participants
meetings 1 ---- N meeting_participants


WHY SEPARATE meeting_participants?
----------------------------------

A meeting has many participants, and a user/guest may participate in many
different meetings.

The participant table also stores meeting-session-specific information:
- display name
- role
- joined_at
- left_at

This is much cleaner than storing only a user_name inside the meeting record.


=========================================
7. PUBLIC MEETING ID / INTERNAL DB ID
=========================================

Do NOT expose the SQLite row ID as the public meeting identifier.

Bad:
    /meeting/52

Better:
    /meeting/84739261504

Internal DB:
    id = 52

Public:
    meeting_code = "84739261504"

Use a collision-resistant 10- or 11-digit style meeting code inspired by
modern video conferencing UX.

Database must enforce:
    UNIQUE(meeting_code)

Generation should still defensively retry on the extremely unlikely event
of a collision.

12. MEETING LIFECYCLE / STATE MACHINE
=====================================

Scheduled meeting:

CREATE
  |
  v
SCHEDULED
  |
 start
  |
  v
ACTIVE
  |
 end
  |
  v
ENDED


Instant meeting:

CREATE
  |
  v
ACTIVE
  |
 end
  |
  v
ENDED


CANCELLED is an optional terminal state for scheduled meetings.


BUSINESS RULES
--------------

- Scheduled meetings cannot be treated as active simply because they exist.
- Instant meetings are active immediately after successful creation.
- Starting a scheduled meeting changes status to active.
- Ending a meeting changes status to ended.
- Recent Meetings should generally derive from ended meetings and/or recent
  participant history.
- Joining an invalid meeting must return a clear not-found response.

=================================
25. HOST CONTROLS
=================================

Required bonus scope:

A. Mute participant.
B. Mute all.
C. Remove participant.

Implementation concept:

Host action
   |
   v
Validate role on server/application state
   |
   v
Broadcast/perform action in realtime
   |
   v
Target participant UI/media changes


SECURITY PRINCIPLE
------------------

Do NOT trust a frontend request like:

{
  "role": "host"
}

The backend should determine whether the current participant is the host.

Meeting ID identifies a meeting.
Meeting ID does NOT by itself authorize host actions.


RECOMMENDED BEHAVIOR
--------------------

Host:
- mute participant.
- mute all.
- remove participant.

Participant:
- can unmute themselves after being muted.
- cannot remove others.
- cannot execute host-only operations.

=================================
28. UPCOMING / RECENT QUERY LOGIC
=================================

Upcoming:

SELECT *
FROM meetings
WHERE scheduled_at > CURRENT_TIMESTAMP
  AND status = 'scheduled'
ORDER BY scheduled_at ASC;


Recent:

SELECT *
FROM meetings
WHERE status = 'ended'
ORDER BY ended_at DESC
LIMIT 10;


Depending on product interpretation, recent history can also include meetings
the current user recently participated in.

===================================
39. WEBRTC INTERVIEW PREPARATION
===================================

Question: What is WebRTC?

Answer:
WebRTC is a browser technology for realtime peer/media communication,
including audio and video.


Question: Why is signaling needed?

Answer:
WebRTC needs a way for communicating parties to exchange session
negotiation information before the media connection can be established.
Signaling can be transported using WebSockets or another application
channel.


Question: What is SDP?

Answer:
Session Description Protocol. It describes the proposed media/session
configuration during negotiation.


Question: What is ICE?

Answer:
Interactive Connectivity Establishment. It helps discover candidate network
paths and determine how endpoints can connect.


Question: What is STUN?

Answer:
A mechanism used to discover public-facing network information for
NAT traversal.


Question: What is TURN?

Answer:
A relay mechanism used when a direct peer-to-peer path cannot be established.


Question: What is an SFU?

Answer:
Selective Forwarding Unit. Participants send media to the SFU, and the SFU
forwards media to the appropriate subscribers.


Question: Why SFU instead of P2P mesh?

Answer:
P2P mesh becomes increasingly expensive as participant count increases
because each participant may need to upload multiple streams. An SFU lets
each participant publish upstream while the server forwards tracks to
subscribers.


====================================
40. FASTAPI INTERVIEW PREPARATION
====================================

Why FastAPI?

Answer:
- Clean REST API design.
- Pydantic validation.
- Async support.
- Automatic API documentation.
- Native WebSocket support.
- Good fit for a realtime-oriented application.

Why not put all logic in routes?

Answer:
Routes should handle HTTP concerns. Business logic belongs in services, and
database operations belong in repositories or dedicated data-access functions.


======================================
41. NEXT.JS / FRONTEND INTERVIEW PREP
======================================

Why Next.js?

Answer:
The assignment requires Next.js. It also provides routing and a React-based
component architecture appropriate for a client-heavy SPA-style application.

Why reusable components?

Answer:
Repeated UI patterns such as MeetingCard, VideoTile, and MeetingControls
should be maintained in one place so the interface stays consistent and
changes do not require duplicate edits.


=========================================
42. DATABASE INTERVIEW PREPARATION
=========================================

Question:
Why separate meetings and participants?

Answer:
One meeting has many participants, and users/guests can participate in many
meetings. The participant table represents this relationship and stores
session-specific data.


Question:
Why is user_id nullable?

Answer:
Authentication is optional. Guests can join by entering a display name.


Question:
Why not use MongoDB?

Answer:
SQLite is explicitly required by the assignment, and the data has clear
relational relationships.


Question:
Why not use the DB integer ID as meeting ID?

Answer:
The internal database ID is an implementation detail. A separate public
meeting code is safer and more appropriate for the user-facing meeting URL.


================================
43. API INTERVIEW PREPARATION
================================

Why REST for meetings?

Because:
- create meeting.
- schedule meeting.
- retrieve meeting.
- validate meeting.
- retrieve upcoming/recent meetings.

These are request/response business operations.

Why realtime for meeting state?

Because:
- participant joined.
- participant left.
- mute event.
- chat message.
- screen share state.

These are event-driven and time-sensitive.
